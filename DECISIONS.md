# Design Decisions

## Key design decisions & tradeoffs

**State management: React Context + `useReducer`, not Zustand/Redux.** One root `RootState` (`src/app/appState.types.ts`), one reducer, one debounced `localStorage` write on every change. For a six-section app where every reviewer question boils down to "is state managed cleanly," a single reducer file you can read top-to-bottom is more legible than a library abstraction, even though Zustand would have been slightly less boilerplate.

**A hand-rolled JSONPath subset, not a library.** `lib/jsonpath/jsonPath.ts` supports exactly what the spec's examples need — dot paths, numeric array indices, one `[*]` wildcard — not full JSONPath (filters, recursive descent, unions). A dependency here would be unjustified surface area for a prototype whose reviewers read the code; the tradeoff is it would need extending if a future connector needed a filter expression.

**Section 5 uses dropdown selectors, not drag-and-drop; Section 6 uses drag-and-drop.** The spec explicitly offers "drag-and-drop or dropdown selectors" for Section 5's field mapping. With exactly 10 fixed canonical targets, a `<select>` per source field is simpler to build, simpler to test, and no less usable than drag targets. Section 6 Part A's field *reordering* has no dropdown equivalent, so that's where dnd-kit earns its place — and its keyboard sensor is what makes the reorder logic testable at all, since jsdom can't simulate native HTML5 drag events.

**OAuth2 "Fetch Token" is simulated, not real.** No real OAuth server exists to test against in this environment, and a real token-URL POST from the browser would almost always fail on CORS anyway — just re-exercising the same failure path Section 6 already covers, without adding real signal. The UI says "(simulated — no live OAuth server available)" rather than quietly pretending.

**CORS/network failures collapse to one honest message.** Browser `fetch()` cannot distinguish a CORS block from a DNS failure or a refused connection — all three throw the identical `TypeError`. Rather than fake a three-way distinction the platform can't actually make, `executeRequest` classifies outcomes into exactly two buckets: `timeout` (the one case a client-side deadline can detect for certain) and `unreachable` (everything else), and the UI says so explicitly. This is visible in Section 1's health check and Section 6 Part C's submission failures alike.

## Working with Claude Code

I asked Claude Code to follow a fixed pipeline for this build — environment check, then plan the scope together before writing anything, then scaffold, then backend-equivalent core logic with tests alongside each piece, then UI section-by-section with tests alongside, then manual browser verification, then docs, then git/GitHub. Before any code, I had it dispatch a Plan sub-agent to produce a full architecture doc (state shape, component breakdown, build order, testing strategy) and explicitly list every spec ambiguity it found rather than silently picking an interpretation. I then resolved those ambiguities myself through a couple of rounds of targeted questions (dropdown vs. drag-and-drop, simulated vs. real OAuth, how to word CORS failures, and git/GitHub visibility) before approving anything.

The one point where I substantially pushed back on its first plan: the initial draft treated JSON-path validation, `{{variable}}` detection, and the mapping export format as implementation details to be improvised during coding. I sent it back with concrete requirements instead — `jsonPath.ts` needed to report *missing* vs. *type-mismatched* fields against a response schema (not just resolve paths), variable detection had to scan header and query-param values in addition to the path (the spec says all three), the `connector-mapping.json` export needed an explicit versioned schema rather than a bare array, all 6 outbound field types needed to be accounted for up front (including `Toggle` rendering as a real switch), `setByPath` needed to handle deep nested-path creation (not just the spec's flat test scenario), and the test setup needed a centralized fetch mock plus explicit `localStorage` quota-exceeded handling. Claude Code folded all of that into the plan before I approved it, and the plan file reflects the corrected version, not the first draft.

During the actual build, its own test suite caught a real bug it had introduced: Section 6 Part B's live Payload Preview recomputes on every keystroke, and while a target JSON path is mid-typed (e.g. just `$`), `setByPath` threw rather than treating that as a normal transient state. The fix — skip mappings whose path doesn't yet resolve to a usable segment — was driven directly by a failing RTL test, not by manual inspection. Separately, manual browser verification (not the automated suite) caught a second real bug: `executeRequest` wasn't setting `Content-Type: application/json` on JSON request bodies, so `jsonplaceholder` silently ignored the submitted payload and echoed back only a new `id` instead of the full record. Both are called out in their respective commits.

## The Admin/User View switch

`state.ui.viewMode` lives in the same persisted `RootState` as everything else, toggled from a control in the `AppShell` header (visible on every route, per spec) but only consumed meaningfully by `OutboundFormsPage`: Admin View renders the builder and mapping panels; User View renders `OutboundFormUser` — the real, validating, submitting form — and nothing else. The two views share one `OutboundFieldRenderer` component: Part A's Live Form Preview calls it in a disabled/non-interactive mode so the preview is provably pixel-identical to what Part C actually renders, rather than being a second, potentially-drifting implementation of "what a text field looks like."

## Productionizing outbound payload construction

Three things I'd add before this touched a real target system:

1. **Schema validation before send.** Right now `buildOutboundPayload` will happily construct and submit a payload whose shape doesn't match what the target endpoint expects — there's no check against the endpoint's own `responseSchema`/expected request shape. A real version would validate the constructed body against a declared JSON Schema (derivable from the endpoint's configured fields) and block submission with a clear error before any network call, rather than relying on the target API's 4xx response to surface a shape mismatch after the fact.
2. **A dry-run mode.** A toggle that runs the full pipeline — validation, mapping, transform, payload construction, auth header injection — and displays the exact request that *would* be sent, without calling `fetch`. This is the natural next step from the already-live Payload Preview, and it's what a QA/reviewer workflow actually needs before trusting a new mapping against a production system.
3. **Server-side audit logging.** The current Request History is a client-only, 10-entry, per-browser log — it disappears on `localStorage.clear()` and was never visible to anyone but the one admin using that browser. A production connector needs a durable, server-persisted audit trail of every outbound submission (who, when, what payload, what endpoint, what response), independent of any one browser's local state.
